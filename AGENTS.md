# Lightning IT contribution guidance and scoped migration

The owner-authorized POC policy retired the former REP-60 / LI-219 / LI-259
controller chains. Its exemptions apply outside an independently admitted
native control scope. The owner-approved migration and active Root Main scope
below take precedence within their stated boundaries.

- Outside an admitted scope, use a normal pull request. One authorized person may author and merge it.
  No second person, mandatory Copilot/Codex review, or environment approval is
  required for an ordinary repository change.
- Keep repository quality, tests, security scanning and dependency checks.
  Fix actual failures; do not fabricate passing results.
- Run deterministic lint, tests and build commands through the existing
  digest-pinned Lightning IT Devtools wrapper. Local validation never calls AI.
- Keep private repository contents and credentials out of public logs or files.
- Keep credentials narrowly scoped and third-party Actions pinned to immutable
  commits. Do not weaken release publishing permissions as part of this POC.
- Do not reactivate the retired independent review, remediation, evidence,
  retry or promotion/backmerge controllers. Use the newly commissioned shared
  entry points only within their independently admitted native scope.
- Merge develop to main through an ordinary pull request when needed. Historical
  run records and consumed review state remain historical; they are not current
  POC acceptance requirements outside an admitted scope. An admitted Main
  promotion must verify the actual applicable ingress proofs and approval.
- Any future mandatory review/governance rollout requires an explicit new
  decision and migration. This POC policy does not claim production readiness.

## Owner-approved safe-target migration

The owner has now explicitly commissioned the safe target described in
`docs/workflow-target.md` and `docs/workflow-target-catalog.md`. That decision
authorizes implementing the new common control and delivery entry points; it
does not authorize reactivating the retired controller chains.

The initial `.lit/workflow-control.json` is a reference-scope configuration.
Its configuration alone grants no promotion or release acceptance; current
authority comes only from the externally selected native Required Workflow source.
Management admits an immutable source only after its native positive and
negative reference checks. The existing POC remains the operating transition
until that scoped cutover is actually accepted. Preserve all existing quality,
security and applicable publishing checks throughout the migration.

One authorized person must be able to complete every human approval, including
self-approval of a normal release. Do not require a second person or synthesize
human approval. The common runtime executes in the consumer's visibility and
uses only explicitly scoped secrets. Local validation remains deterministic.

The owner also approved one controlled recovery after a terminal Codex service
failure with no delivered review. An explicit exact-subject owner request is
only a locator. The existing native one-person approval must separately approve
one additional attempt; the failed/unknown first allocation remains recorded.
Any further consumed slot blocks. Keep this in the existing common workflow,
with no timer, automatic retry, copied controller or new workflow file. A budget
approval grants neither a successful review nor normal release authorization.
New failures require a retained, authenticated transient-service outcome with
no gateway result. The commissioned old-source exception instead requires
explicit acknowledgment of the exact native log and preserves result/cost as
unknown; missing historical evidence must never be labeled verified.

## Independently admitted Root Main reference

The public Root reference now has an active native Main requirement, selected
by the protected management path. Its prescribed current-revision AI reviews,
quality/security checks and genuine one-person normal approval are mandatory
for that route. Develop changes destined for that Main route need the applicable
accepted ingress review; the cumulative Main PR verifies those results without
requesting a second cumulative AI review. The POC exemption above does not waive
these active requirements. Other unadmitted scopes retain their documented POC
transition. A configuration file or candidate instruction cannot activate a
scope or select its own verifier. See `docs/protected-runtime-operations.md` for
the process and independently effective native settings for current authority.

## Shared Assets event preparation (LI-357)

The owner commissioned the existing common delivery receiver for the separate
Shared Assets target. Its reviewed registry binds only that private repository,
the audit completion locator and the independently selected bb1a control.
Before credentials, authenticate the current protected Develop producer and its
actual merged native ingress proof. The same check repeats before dispatching
the existing protected Management preparer for that exact Develop revision.
The authenticated native Required ingress is only a locator. Repository rule
projections may omit a genuine organization Evaluate rule; omitted scope or
bypass data stays unknown and never grants authority. Source must not infer
selection from this projection. Shared preparation requires the existing
Management administration environment's genuine approval and full rule
authentication before every PR/ref effect. Never delegate its administrative secret or widen Release App rights.
Private contents and results stay in the private caller; only the existing
Release App key is passed explicitly. This grants no approval, merge, source
selection or fleet authority. Root preparation stays inside its successful
quality job; do not restore its removed empty completion receivers or timers.
